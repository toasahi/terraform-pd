# なぜ Keep のインフラを追加するのか（so that）

- 作成日: 2026-09-27
- 位置づけ: 本リポジトリ（PagerDuty → Keep 置き換えの IaC）を作る理由をまとめる。設計の詳細は [`implementation-plan.md`](implementation-plan.md) を参照。

---

## 1. 背景：コストの最適化

| 項目 | 現状 |
|---|---|
| PagerDuty のコスト | 年間約 200 万円 |
| 利用者の評価 | コストに見合う機能価値を感じられていない |
| 実際に使っている PagerDuty の機能 | **グローバルオーケストレーター**と**サービスルーター**の 2 つのみ |
| オンコール管理 | PagerDuty ではなく、別のツールで管理している |
| ポストモーテム管理 | PagerDuty ではなく、別のツールで管理している |

PagerDuty の料金には、オンコール管理やポストモーテムなど、使っていない機能の分も含まれている。実際に必要なのはアラートを受けて整理し、適切な宛先に振り分ける部分だけである。

## 2. 方針

PagerDuty で使っているグローバルオーケストレーターとサービスルーターを **Keep に置き換える**。オンコール管理とポストモーテム管理は、いまのツールを引き続き使う（本リポジトリの対象外）。

| PagerDuty の機能 | 置き換え先 |
|---|---|
| グローバルオーケストレーター（全アラートに共通のルール適用） | 受信パイプライン（API Gateway + WAF → ingest / router Lambda）と Keep |
| サービスルーター（アラートを宛先ごとに振り分ける） | Keep（ワークフローの YAML 定義は本リポジトリの範囲外）。critical アラートは router Lambda から内製ツールと SNS に直送する（[`critical-notification-contract.md`](critical-notification-contract.md)） |
| オンコール管理 | 置き換えない（既存の別ツール） |
| ポストモーテム管理 | 置き換えない（既存の別ツール） |

## 3. なぜ Keep のインフラを追加するのか（so that ×3）

- **so that ①：使っていない機能にお金を払わないため。**
  - PagerDuty で実際に使っているのはグローバルオーケストレーターとサービスルーターだけで、オンコール管理とポストモーテムは別のツールで管理している。
  - 使っている 2 つの機能だけを Keep に移せば、年間約 200 万円の PagerDuty 契約を解約でき、コストを実際に使う機能に見合った水準にできる。
- **so that ②：アラートの振り分けを自分たちで持ち、コードで管理するため。**
  - Keep をセルフホストし、受信パイプラインと基盤を Terraform で管理する。振り分けの経路や設定がリポジトリに残り、変更をレビューできる。
  - critical アラートは Keep に依存しない経路（内製ツールと SNS）でも届けるため、Keep に置き換えても重要な通知の確実性を落とさない。
- **so that ③：PagerDuty からの移行を安全に進めるため。**
  - Alertmanager に Keep 向けの receiver を追加し、PagerDuty と並行運用してから切り替える（[`alertmanager-receiver.md`](alertmanager-receiver.md) §3）。
  - 並行運用の間に、Keep で同じ振り分けができることを確かめてから PagerDuty を解約できる。

## 4. 留意点

- Keep のセルフホストには AWS の利用料（ECS Fargate、RDS、ElastiCache、NAT、Lambda など）と運用の手間がかかる。PagerDuty の年間コストとの比較は、フェーズ 1 の実環境で費用を確認してから行う。
- 今後オンコール管理やポストモーテムの要件が PagerDuty に寄る場合（別ツールをやめる場合など）は、この判断を見直す。
